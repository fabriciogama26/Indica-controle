Tela: Auditoria SaaS

Visao geral
-----------
- Tela administrativa (somente leitura) com 3 abas para consultar o que o sistema ja registra
  de auditoria, sem agregacao anterior: Alteracoes, Acessos e Erros.
- Aba Alteracoes: le `app_entity_history` (historico generico ja gravado por dezenas de modulos
  de cadastro). Mostra quem alterou o que, em qual tela, com diff de campos.
- Aba Acessos: le `login_audit` (login, logout, falha e motivo de saida, incluindo inatividade).
  Ja existia o dado, nao existia leitura nem tela — gap que estava documentado em
  `Auditoria/Auditoria_Login_Acessos_SaaS.txt`.
- Aba Erros: le `app_error_logs` (erros capturados manualmente pelas telas via
  `useErrorLogger`/Edge Function `log_error`).
- Nao inclui o historico da Permissao de Intervencao (`pi_history`) nem cria page_key/migration
  em `app_pages` — ver secao "Decisoes desta entrega" e "Pendencia de padronizacao" abaixo.

Arquitetura
-----------
- Rota: `src/app/(dashboard)/auditoria/page.tsx`
- View (shell + abas): `src/modules/dashboard/auditoria/AuditPageView.tsx`
- Aba Alteracoes: `src/modules/dashboard/auditoria/ChangesTab.tsx`
- Aba Acessos: `src/modules/dashboard/auditoria/AccessTab.tsx`
- Aba Erros: `src/modules/dashboard/auditoria/ErrorsTab.tsx`
- Cliente HTTP das 3 abas: `src/modules/dashboard/auditoria/api.ts`
- Tipos compartilhados: `src/modules/dashboard/auditoria/types.ts`
- Estilo: `src/modules/dashboard/auditoria/AuditPageView.module.css`
- Rotas de API: `src/app/api/auditoria/{alteracoes,acessos,erros,telas}/route.ts` (todas finas,
  so delegam para `src/server/modules/auditoria/handlers.ts`)
- Handlers (parse de filtros/paginacao + guard admin): `src/server/modules/auditoria/handlers.ts`
- Queries (Supabase, filtros e paginacao): `src/server/modules/auditoria/queries.ts`
- Guard admin-only: `src/lib/server/appUsersAdmin.ts` (`resolveAdminOperator`)
- Guard de rota (menu + redirect): `src/lib/auth/authorization.ts` (`ADMIN_ONLY_ROUTE_PREFIXES`)
- Navegacao: `src/components/layout/AppShell.tsx`

Decisoes desta entrega
-----------------------
- Tela restrita a admin do tenant, seguindo o MESMO padrao de `/permissoes`: entrou em
  `ADMIN_ONLY_ROUTE_PREFIXES` (`authorization.ts`), NAO por `page_key`/`app_pages`. Por isso nao
  ha migration nesta entrega, nao ha entrada em `ROUTE_PAGE_KEYS`, e as rotas de API usam
  `resolveAdminOperator` (mesmo guard de `app-users/[userId]/permissions/route.ts`) em vez de
  `requirePageAction`. Diferenca visual do precedente: `/permissoes` so aparece pelo icone de
  engrenagem; `/auditoria` ganhou item proprio em `menuSections` (secao "Auditoria"), decisao
  explicita do usuario — some do menu sozinho para quem nao e admin via `canAccessRoute`.
- Todas as queries usam o client admin (`service_role`, bypassa RLS) resolvido por
  `resolveAdminOperator`. Por isso TODA query em `queries.ts` filtra `tenant_id` manualmente no
  codigo (nao existe rede de seguranca de RLS aqui) — atencao redobrada em qualquer alteracao
  futura nesses arquivos.
- Busca por usuario (nome/matricula) nas 3 abas NUNCA usa `.or()` com texto livre do cliente
  (convencao ja usada em `programacao-normalizada/queries.ts`): resolve primeiro os ids de
  `app_users` que casam com o texto via `.ilike()` parametrizado em 3 colunas separadas
  (`resolveUserIdsByQuery`), depois filtra a tabela principal por `.in("created_by"/"user_id",
  ids)`. Retorno `null` = sem filtro; array vazio = "nenhum usuario casa", encerra em zero
  resultados sem consultar a tabela principal.
- Usuario do tenant = tenant de origem (`app_users.tenant_id`) OU vinculo em
  `app_user_tenants`, ATIVO OU INATIVO (ver "Atualizacao 2026-09-14"). Vale para a busca
  (`resolveUserIdsByQuery`) e para o nome/matricula exibidos (`fetchUserSummaries`). O vinculo
  inativo conta de proposito: a Auditoria le historico e quem agiu no tenant precisa continuar
  identificado depois de desligado — diferente de `fetchTenantLinkedAppUsers` (telas
  operacionais), que so aceita vinculo ativo.
- Exportacao CSV segue o MESMO padrao de Pessoas (`/api/people/export`): endpoint dedicado
  `GET /api/auditoria/{alteracoes,acessos,erros}/export` que le TODOS os registros que casam
  com o filtro atual via `loadAllRows` (nao so a pagina carregada), com teto de seguranca
  `MAX_EXPORT_ROWS = 20000` e aviso de "exportacao parcial" quando bate no teto. Frontend usa
  `useExportCooldown` (10s) para nao deixar disparar exportacao em sequencia.
- Sem pareamento LOGIN/LOGOUT por `session_ref` (duracao de sessao) nesta entrega — cada evento
  aparece como uma linha independente, na ordem cronologica. `session_ref` NAO vai no payload
  nem no select (removido em 2026-09-14 — ver motivo de seguranca na atualizacao dessa data);
  um pareamento futuro deve ser feito no servidor, devolvendo so a duracao.

Filtros, auto-complete e listagem
---------------------------------
- Aba Alteracoes (`GET /api/auditoria/alteracoes`): tela (`moduleKey`, populado por
  `GET /api/auditoria/telas` a partir de `app_pages.name`), usuario/matricula (`userQuery`),
  tipo de alteracao (`changeType`: UPDATE/CANCEL/ACTIVATE — mesmo CHECK de `app_entity_history`),
  codigo do registro (`entityCode`, `ilike`), intervalo de datas (`dateFrom`/`dateTo` sobre
  `created_at`). Paginacao 20/pagina, ordenado por `created_at desc`.
- Aba Acessos (`GET /api/auditoria/acessos`): usuario/matricula (`userQuery`), status
  (SUCCESS/FAILED), evento (LOGIN/LOGOUT), motivo (lista fechada observada em `login_audit`:
  USER_LOGOUT, IDLE_TIMEOUT, TOKEN_EXPIRED, USER_NOT_FOUND, INACTIVE, AUTH_INVALID), origem
  (APP/SITE), intervalo de datas sobre `event_at`. Ordenado por `event_at desc`.
- Aba Erros (`GET /api/auditoria/erros`): usuario/matricula (`userQuery`), severidade (select
  com ERROR/WARNING/INFO — a coluna e texto livre sem CHECK, na pratica so `ERROR` e gravado
  hoje), tela (`screen`, `ilike` parcial — texto livre por tela, nao um catalogo fechado), origem
  (WEB/APP — `source`, granularidade "de onde partiu a requisicao", NAO "API vs front"; ver
  pendencia abaixo), intervalo de datas sobre `created_at`. Ordenado por `created_at desc`.
- Todas as 3 rotas usam `parsePagination` (`src/lib/server/apiHelpers.ts`), `.range()` (nunca
  `.limit()` acima do teto do PostgREST) e `{ count: "exact" }` para o total da paginacao.

Boas praticas
-------------
- Restringir a tela a perfis administrativos (ja garantido por `ADMIN_ONLY_ROUTE_PREFIXES`).
- Nunca adicionar filtro de texto livre via `.or()` nas 3 tabelas principais — seguir o padrao
  `resolveUserIdsByQuery` (resolver ids em `app_users` primeiro, depois `.in()`).
- Toda nova coluna de filtro precisa continuar filtrando `tenant_id` explicitamente no `queries.ts`
  — nao ha RLS a favor aqui (client admin).
- Nunca ler linha de outro tenant para "completar" a visao de um usuario multi-tenant (ex.: logins
  gravados no tenant de origem). O vinculo so muda QUEM e identificado, nunca QUAIS linhas
  aparecem — as linhas continuam presas a `tenant_id = tenant ativo`.
- Nunca exibir linhas com `tenant_id` nulo: em `login_audit` sao tentativas com usuario
  inexistente, com `login_name` digitado por quem nao esta autenticado.
- Identidade na aba Erros vem de `user_id` (derivado do JWT pela `log_error`), nunca de
  `app_error_logs.matricula`/`login_name`: a Edge Function aceita a matricula enviada pelo cliente.
- `login_audit` e `app_error_logs` sao classificadas (auditoria interna,
  `Auditoria/15-supabase-implicit-row-cap.md`) como tabelas que "crescem monotonicamente e nunca
  sao podadas" — o filtro de intervalo de datas nas abas Acessos e Erros nao e cosmetico, e a
  unica forma pratica de manter a consulta rapida com o tempo.

Pendencia de padronizacao (fora de escopo desta entrega)
----------------------------------------------------------
- `permission_intervention` grava historico em tabela propria `pi_history`, nao em
  `app_entity_history` (ver comentario em `supabase/migrations/429_create_permission_intervention.sql`
  linha ~384). Motivo documentado: o CHECK de `change_type` de `app_entity_history` so aceita
  `UPDATE`/`CANCEL`/`ACTIVATE`; a PI usa hoje 10 valores de `action_type` (`CREATE`, `LINK_AUTO`,
  `UPDATE`, `UPDATE_EXECUTION_PLAN`, `CANCEL`, `ISSUE`, `MARK_READY`, `REOPEN`, `LINK_MANUAL`,
  `RELINK` — o comentario da migration cita `GENERATE_DOCUMENT`, mas esse valor nunca foi
  implementado em codigo).
- Diferenca de modelo de seguranca, nao so de CHECK: `app_entity_history` aceita `INSERT` direto
  de qualquer `authenticated` (varios handlers TS fazem `.from("app_entity_history").insert(...)`
  direto); `pi_history` bloqueia todo `INSERT` direto — so entra via RPC `SECURITY DEFINER`
  (`pi_append_history`). Padronizar as duas exige decidir qual postura vale para todo mundo, nao
  so alargar um CHECK.
- Diferenca de volume por natureza: o fluxo de PI grava dezenas de linhas por registro ao longo
  de um unico ciclo de aprovacao (toggle pronto/reabrir, vinculo, emissao); os demais modulos so
  gravam em update/cancel/activate. `pi_history` tem 1 indice de 3 colunas contra 2 indices (um de
  5 colunas) em `app_entity_history` — mais leve por linha, mas por atender uma unica entidade,
  nao por ser mais otimizada.
- Achado extra: dentro do proprio modulo PI ja existe uma 3a variacao — `pi_settings`
  (configuracao do contrato) usa `app_entity_history`, nao `pi_history`, por decisao de
  granularidade (registro vs contrato inteiro; comentario em
  `supabase/migrations/431_pi_settings_roles_and_contact_source.sql` linha ~127).
- Nao ha, no codigo ou em `TASKS.md`, nenhum plano ja aberto de unificacao. A migration que criou
  `pi_history` argumenta explicitamente que alargar o CHECK de uma tabela compartilhada por ~15
  modulos e mais arriscado do que manter tabela propria — qualquer proposta futura de padronizacao
  precisa lidar com esse argumento e com a diferenca de modelo de seguranca acima, escolhendo a
  opcao de menor impacto de I/O e risco, e nao entra nesta tela sem tarefa dedicada.

Proximos passos (nao implementados nesta entrega)
---------------------------------------------------
- Separar, na aba Erros, "erro de API" de "erro de tela" dentro do `source = WEB` — hoje nao ha
  coluna para isso; exigiria campo novo (`origin`/`layer`) escrito explicitamente nos ~41 pontos
  de chamada de `useErrorLogger`. Tambem nao existe captura automatica de excecao (sem
  `error.tsx`/`global-error.tsx`, sem error boundary, sem catch em rota de API) — hoje so aparece
  na tela o que cada tela decidiu logar manualmente em `catch`.
- Parear LOGIN/LOGOUT por `session_ref` na aba Acessos para mostrar duracao de sessao.
- Decisao de padronizacao `pi_history` vs `app_entity_history` (ver secao acima) — tarefa
  dedicada, fora desta tela.
- Seguranca (levantado em 2026-09-14, etapas 2 a 4 do plano; ver atualizacao dessa data):
  - RLS de leitura: as policies de SELECT de `login_audit`, `app_error_logs` e
    `app_entity_history` usam `user_can_access_tenant(tenant_id)`, entao QUALQUER membro do
    tenant (inclusive `viewer`) le essas tabelas via `/rest/v1` com o proprio JWT — a tela e
    admin-only so na API. Proposta: migration trocando as 3 policies para
    `user_is_admin_in_tenant(tenant_id)`, depois de conferir as policies no banco vivo (o CLI nao
    estava linkado na analise). As rotas usam `service_role` e nao dependem dessas policies.
  - CSV: `escapeCsvValue` (`src/lib/utils/csv.ts`) nao neutraliza celula iniciada por
    `= + - @`; a exportacao da aba Erros leva `message`/`screen`, texto controlado por qualquer
    usuario logado. Corrigir sem quebrar numero negativo de `formatCsvNumber` (afeta todas as
    exportacoes do sistema).
  - Aba Acessos multi-tenant: LOGIN/LOGOUT sao gravados no tenant de origem (o login acontece
    antes da escolha de contrato). NAO resolver lendo linhas do tenant de origem (quebra o
    isolamento). Caminho seguro: evento de entrada no contrato gravado no servidor com o tenant
    validado por `resolveAuthenticatedAppUser` (ex.: `POST /api/auth/active-tenant`); falta
    definir o momento para nao-admin. Nao trocar o `tenant_id` do LOGIN: a `logout` compara com
    `app_users.tenant_id` e deixaria de achar a sessao.
  - Aba Erros multi-tenant: `log_error` grava `app_users.tenant_id` (origem). Caminho seguro: rota
    Next com `resolveAuthenticatedAppUser` (tenant do cookie `httpOnly` validado no servidor),
    sem aceitar tenant/matricula do cliente. Na mesma tarefa, `log_error` deixa de aceitar
    `body.matricula`.
  - `logout`: fallback `reason=TOKEN_EXPIRED` + `session_ref`/`login_audit_id` grava LOGOUT sem
    sessao valida (so anon key). Tratar em tarefa propria — ha 349 logouts legitimos por esse
    caminho.

Atualizacao 2026-09-14

- Corrigido: usuario multi-tenant aparecia como "Nao identificado" e nao era encontrado pela busca
  por usuario. Causa: `fetchUserSummaries` e `resolveUserIdsByQuery` filtravam so
  `app_users.tenant_id = tenant ativo`, mas usuarios multi-tenant mantem o `app_users.id` do tenant
  de origem e operam nos demais por `app_user_tenants`. Evidencia (leitura em producao antes da
  correcao): no tenant INDICA SERVICO - MACAE, 29 de 39 linhas de `app_entity_history` (74%) sem
  autor identificado, todas de um usuario com origem em INDICA SERVICO - ANGRA; 6 vinculos ativos
  fora do tenant de origem.
  - Antes: usuario = so tenant de origem.
  - Depois: usuario = tenant de origem OU vinculo em `app_user_tenants` (ativo ou inativo). As
    linhas listadas NAO mudam — continuam filtradas por `tenant_id = tenant ativo`; so a
    identificacao do autor muda.
  - Consultas continuam presas ao tenant: `app_users` por `tenant_id`, ou restrito a ids cujo
    vinculo com o tenant foi confirmado em `app_user_tenants`. Ids em lotes de 200
    (`loadRowsInChunks`) e leituras via `loadAllRows`/`loadRowsInChunks` (sem truncamento
    silencioso). Erro de banco nessas consultas passa a virar 500 em vez de ser engolido e
    exibido como "Nao identificado".
- Corrigido (leitura): aba Erros exibia `app_error_logs.matricula`, valor que a Edge Function
  `log_error` aceita do body do cliente (qualquer usuario logado podia registrar erro com a
  matricula de outro), e `login_name`, que a funcao nunca grava (coluna Usuario sempre vazia).
  - Antes: `ErrorLogItem.loginName`/`matricula` lidos da linha.
  - Depois: `ErrorLogItem.userName`/`userMatricula` resolvidos por `user_id` via
    `fetchUserSummaries`, no mesmo formato da aba Alteracoes; as duas colunas sairam do select.
  - A gravacao em `log_error` ainda aceita `body.matricula` — pendente (ver "Proximos passos").
- Removido: `session_ref` do select e do payload da aba Acessos (`AccessLogItem.sessionRef`).
  Nenhuma tela usava, e a Edge Function `logout` aceita `session_ref` + `reason=TOKEN_EXPIRED` sem
  sessao valida para gravar LOGOUT — expor o valor permitia forjar o horario de saida.
- Descartado nesta analise: resolver a aba Acessos de usuario multi-tenant lendo linhas do tenant
  de origem. Quebraria o isolamento (logins em outro contrato, tentativas de senha errada,
  historico anterior ao vinculo). Alternativa segura registrada em "Proximos passos".
- Validacao executada: `npx tsc --noEmit` e `npm run lint` verdes; checagem somente-leitura das
